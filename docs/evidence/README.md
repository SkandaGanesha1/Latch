# LATCH — Evidence Archive

Every number this project quotes comes from a file in this
directory. This index says which file proves which claim, how to
regenerate each one, and — just as important — what is **not**
proven here.

A judge without a QNX SDP licence cannot rebuild the IFS, so this
archive is the target proof. It is raw console output, not a
summary written for you.

## 3. How to regenerate each one

The **legacy archive** (`build/`, `derived/`, `host-sim/`, `on-target/`,
`resolution/`, `tape/`) is produced by one tool:
`tools/capture_evidence.py`. Nothing there is hand-edited.

```bash
source ~/qnx800/qnxsdp-env.sh

cd latch

# Everything except the QEMU run (~20 s, no QNX licence needed beyond the SDP)
python3 tools/capture_evidence.py --all

# A fresh on-target capture: boots QEMU AArch64 `virt` and drives it (~5 min)
python3 tools/capture_evidence.py on-target

# Or, through the Makefile
make -C qnx evidence          # --all
make -C qnx evidence-on-target # the QEMU run

# Re-derive derived/on-target-metrics.txt from the ARCHIVED raw console
# dump (analysis only -- no QEMU, no licence, no guest image; the
# consistency gate DIFFs a fresh derivation against the committed file)
make -C qnx evidence-rederive-on-target
```

The **GOVERNOR captures** (`governor/`) are raw outputs of their named
tools, each with its own regeneration command:

```bash
# governor-qemu-verify.txt + governor-qemu-console.txt -- the scripted
#   GOVERNOR profile's ON-TARGET capture: the cross-build, the mkifs
#   listing, the structured runtime report and the raw serial
#   transcript.  The archive is written ONLY when the run passes.
GUEST_IMAGE=/abs/path/to/linux-6.12/arch/arm64/boot/Image \
  make -C qnx evidence-governor-qemu

# governor-metrics.txt -- the attack scorecard (host-sim build); the
#   tick and attack counts in it are measured, not typed in by hand
python3 tools/governor_metrics.py --out docs/evidence/governor/governor-metrics.txt

# homeostat-runtime-proof.txt -- the HOMEOSTAT outer-loop runtime proof
#   (unit test + the 5-scenario supervisor-level proof)
python3 tools/homeostat_e2e.py \
  qnx/build/host-sim/latchctl qnx/build/host-sim/latch-ingest \
  qnx/build/host-sim/latchd qnx/contracts/governor_servo.manifest

# infer-qemu.txt + infer-qemu-console.txt -- the EXPERIMENTAL in-guest
#   language-model profile: the nominal run and the attack run, both on
#   target.  The archive is written ONLY when BOTH runs pass.
GUEST_IMAGE=/abs/path/to/linux-6.12/arch/arm64/boot/Image \
  make -C qnx evidence-governor-infer

# secpol-audit.txt -- the SECURITY-POLICY GENERATION AUDIT: the
#   disposable, unrestricted secpolgenerate image runs the 235-frame
#   scenario and the generator's observed DELTA, ERRORS and UNUSED
#   files are captured.  The archive is written ONLY when the run
#   passes; the DISPOSITION of the delta is the written review
#   (docs/secpol-audit-review.md), not this capture.
GUEST_IMAGE=/abs/path/to/linux-6.12/arch/arm64/boot/Image \
  make -C qnx evidence-secpol-audit

# feedback-transport.txt + the two raw console transcripts -- the LFBK
#   FEEDBACK TRANSPORT and the VERDICT CONTROL LOOP, in two QEMU boots:
#   W4 asks whether a verdict reaches the freestanding guest at all
#   (the guest's own polling must see the sequence number CHANGE), and
#   W5 asks the question that matters -- when the TRUSTED supervisor
#   refuses the guest's proposal, does the guest find out, and does it
#   STOP asking?  The archive is written ONLY when BOTH runs pass.
GUEST_IMAGE=/abs/path/to/linux-6.12/arch/arm64/boot/Image \
  make -C qnx evidence-governor-feedback

# LATENCY.md + latency-console.txt -- the U-4 DECISION-LATENCY
#   MEASUREMENT: the trusted supervisor's own per-tick decision
#   latency, sampled once per tick for more than a MILLION ticks and
#   aggregated in a histogram ON THE TARGET.  One QEMU boot, ~40 min
#   of soak.  The archive is written ONLY when the run passes, and
#   every figure in LATENCY.md is read back out of the TARGET's own
#   report -- none of them is typed in by hand.
GUEST_IMAGE=/abs/path/to/linux-6.12/arch/arm64/boot/Image \
  make -C qnx evidence-governor-latency
```

`governor-qemu-console.txt` is the full serial console of a GOVERNOR QEMU
session, `governor-status-transition.txt` the `latchctl status` snapshots
from it, `governor-tape.csv` the evidence-tape rows it produced,
`governor-host-sim.txt` the host-sim run log,
`homeostat-runtime-proof.txt` the HOMEOSTAT outer-loop proof (unit test
plus the contraction / recovery / contracting-only / default-off /
fail-closed scenarios), and
`governor-manifest-verify.txt` the `latchctl manifest-verify` output for
the signed contract, and `infer-qemu.txt` / `infer-qemu-console.txt` the
EXPERIMENTAL in-guest language-model captures. `feedback-transport.txt` is
the LFBK FEEDBACK-TRANSPORT and VERDICT-CONTROL-LOOP capture: the W4
transport measurement and the W5 control-loop measurement, each with the
guest's own report and the verifier's own verdict, and with an explicit
"WHAT THIS DOES NOT PROVE" section. `feedback-transport-console.txt` and
`feedback-verdict-console.txt` are the two raw serial transcripts behind
it, verbatim and complete — the PL011 console echoes every record several
times, so the summary lists each **distinct** marker once and the raw
files keep every copy. `secpol-audit.txt` is the
SECURITY-POLICY GENERATION AUDIT: the raw observation of what an
unrestricted `secpolgenerate` saw while the 235-frame scenario ran.
It is an OBSERVATION, not a rule set -- the disposition of every entry
is the written review at `docs/secpol-audit-review.md`, and no rule
generated by the audit was accepted. They are raw captures, not
summaries; the regeneration commands above are the ones with dedicated
tooling.

`LATENCY.md` is the U-4 DECISION-LATENCY MEASUREMENT: the trusted
supervisor's own per-tick decision latency, sampled once per tick,
aggregated in a histogram ON THE TARGET and read back through the
output-only devctl `latchctl latency`. `latency-console.txt` is the raw
serial transcript behind it. **The figures in it are a TCG OBSERVATION
on the QEMU AArch64 `virt` target — NOT a WCET, and not a claim about
physical hardware**; a percentile there is a bucket range, not an exact
value, and the file says so in its own "HOW TO READ THE PERCENTILES"
section. It replaces a WITHDRAWN claim, not a withdrawn measurement: the
old "61 us WCET" row never had a reproducible source at all.

The `history`, `tape` and `resolution` scenarios read the raw console
logs of the bring-up from `/tmp` (override with `--raw-dir`). If those
are gone, the `on-target` scenario produces a fresh canonical session
and the rest of the archive follows from it.

## 6. What is NOT proven here

Stated plainly, because a claim the evidence does not cover is worse
than no claim at all.

- **The horn does not move on this target.** The QEMU AArch64 `virt`
  image runs `latchd -n` (mock I²C). There is **no PCA9685** on the
  QEMU machine and no horn. The Raspberry Pi 4B build is the same
  `latchd` binary with the real `i2c-bcm2711` bus and the PCA9685
  attached — that is the take that moves the horn. **Do not mix the
  two sentences.**
- **The Raspberry Pi 4B path is unexecuted.** No Pi 4B hardware was
  available. The buildfile and the qvmconf are correct and are
  checked by `tools/consistency_check.py`, but nothing here proves
  the Pi boots.
- **The latency numbers are not a WCET.** They are measured
  decision-cycle latencies under **QEMU TCG** (pure software
  emulation of AArch64 on an x86_64 host). TCG timing is not the
  target's timing. Report the last and the max latency, in cycles
  and in nanoseconds, against the manifest's `timing.wcet_budget_us`,
  and name the machine.
  The **U-4 measurement** (`governor/LATENCY.md`) is a *distribution*
  rather than a pair, but it carries the **same** caveat and a
  stronger one: under TCG the supervisor shares host cores with the
  guest and with QEMU itself, so its maxima are the **host's**
  scheduling noise, not the supervisor's own worst case. Its
  percentiles are **bucket ranges**, not exact values, and its
  workload is a HOLD at 100 mrad — one workload, not every workload.
  **It must never be quoted as a WCET, and it says so itself.**
- **No certification claim.** No ASIL, no SIL, no ISO 26262, no IEC
  61508, no IEC 62304. This is a **measured fail-closed runtime
  filter**, and the faults are visible on camera.
- **The guest's console markers are cosmetic.** The PL011 console is
  slow and the kernel's console driver drops entries under load, so
  the guest's phase markers may be missing from the guest console
  log. The **host's** evidence tape is complete, and it is what the
  claims rest on.
- **The security policy IS enforced on every boot — and it HAS NOW
  BEEN AUDITED, but the audit is PARTIAL and it accepted NOTHING.**
  `qnx/latch_qemu.build` pushes the compiled policy with `secpolpush`
  at boot, and pushing the policy is what *triggers* enforcement
  (QNX SDP 8.0: *"Pushing the security policy (using secpolpush) triggers
  policy enforcement"*). So the `latch/actuator` ability's fail-closed
  behaviour is demonstrated **under an enforced policy** — that is
  `latch_verify` steps 5a/5b/5c. (`secpollaunch` is a different utility
  entirely — a setuid-root launcher — and is not the enforcement
  mechanism.)
  The `secpolgenerate` audit **has** been run
  (`governor/secpol-audit.txt`, reviewed in `docs/secpol-audit-review.md`),
  and it found exactly **one** actionable least-privilege item:
  `qvm_host_t` holds the **unrestricted** `settypeid` ability, and the
  generator observed the one transition it makes — `settypeid:latch_ingest_t`.
  That narrowing is **recorded, NOT applied**: the audit's observation is
  a **SUPERSET** (the audit image runs the generator *unrestricted*), so
  adopting a rule from it on the strength of one run is the mistake the
  audit exists to prevent. It must be validated on the **enforced**
  image in its own reviewed change.
  What the audit does **NOT** cover: the I²C plant (the QEMU target runs
  `latchd -n`, mock mode), the Raspberry Pi 4B board (no Pi BSP is
  installed here), the guest-lifecycle channel (`guest_ctl_t` — covered
  by the VM-kill capture instead), the legacy 84-frame verifier and
  `latch_verify_t`, `latchctl_t`'s actuator ability, and every failure
  path. **A rule the workload never touched is UNKNOWN to the audit, not
  SAFE.** And the audit's `unused` file is **not** a removal list: it
  contradicts facts the run itself establishes, because the unrestricted
  run bypasses the ability checks it would otherwise observe as uses.
- **One platform, one architecture.** Everything here is AArch64
  on QEMU `virt`. Nothing here is a claim about x86_64 QSTI, about
  the Pi's real I²C bus, or about any other guest OS.
- **The in-guest language model is an EXPERIMENT, and the model is
  not good.** The 135M-parameter model proposes `-20 mrad` because
  that is what the prompt's worked example shows it; it is not a
  competent controller, and nothing here claims it is. What the
  experiment proves is the **boundary**: an untrusted model that
  runs *inside* the guest still cannot move the plant outside the
  signed envelope. The attack run changes only the PROMPT, not the
  model, the binary, the grammar or the contract.
- **The in-guest inference profile is not the scripted profile.** It
  is a SEPARATE bootable image (`qnx/latch_qemu_infer.build`) that
  carries a 209 MiB read-only asset disk with the model and the
  inference binary on it. The scripted GOVERNOR profile is
  unchanged and is still what the 235-frame verification exercises.
  The two profiles are judged by the SAME signed contract
  (`governor_servo.manifest`, byte for byte).
- **The feedback channel now EXISTS and is measured, but the
  EXPERIMENTAL inference profile does not yet READ it.** The LFBK
  transport and the verdict control loop are proven on target
  (`governor/feedback-transport.txt`): the trusted supervisor publishes
  its own verdict, the freestanding guest decodes and correlates it,
  and the guest **stops** when it is told no. What is still **not**
  proven is an **observe→plan→propose→observe** loop driven by the
  language model: the inference profile (`qnx/latch_qemu_infer.build`)
  does not consume the channel yet, so that experiment demonstrates one
  supervised proposal, not a closed loop. The scripted W5 profile closes
  the loop with a **deterministic** guest policy, which is the
  deliberate choice — the loop's correctness does not depend on a
  135M-parameter model.
- **The feedback transport is ADVISORY, and carries no authority.** A
  verdict crosses the channel; the ability to move the plant does not.
  The supervisor's own dead-man is the fail-closed path, and it fails
  closed whether or not the channel exists. A guest that stops asking
  when it is refused is a guest that stops asking — the plant's safety
  never depended on the guest continuing to propose, because the
  supervisor holds the actuator ability alone.
- **The model's first proposal is computed BEFORE the supervisor's
  session opens.** That is deliberate: a console line on the QEMU
  guest costs 57-88 ms of guest time, which is most of the signed
  100-tick lease, so the announcement is paid while no lease is
  running and the session opens with the proposal already in hand.
  The lease is then held across the model's SUBSEQUENT turns, and
  the verifier checks that it is still held 25 s later.

## 7. The archive cannot rot

`make -C qnx evidence-check` re-runs the host-sim capture and
compares the signature against the archived one. CI runs it on
every push: if the code drifts away from the archived evidence, the
build fails rather than the submission quietly becoming false.

> **The current canonical session is `docs/evidence/on-target/CURRENT-SESSION.txt`** -- a stable pointer to the timestamped capture family, so this file never has to be rewritten when a capture is re-run.
