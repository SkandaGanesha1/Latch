## 1. What was run

The audit boots the **disposable, unrestricted** `secpolgenerate` image —
`qnx/latch_qemu_governor_secpol_audit.build`, generated by
`tools/generate_secpol_audit_build.py` from `qnx/latch_qemu_governor.build`.
It is never a deployment image, and the enforced image
(`qnx/latch_qemu_governor.ifs`) is built from the unmodified buildfile.

The image runs `secpolgenerate -u -t 100`, lets the **235-frame scripted
guest scenario** run to completion, and then reads the generator's
observation files through a development-only reader
(`qnx/latch_secpol_dump.c`, linked **only** into the disposable image).

| observation file | bytes | what it is |
|---|---:|---|
| `/dev/secpolgenerate/policy` | 2004 | the DELTA — the rules the generator says would have been needed on top of the base policy |
| `/dev/secpolgenerate/errors` | 376 | the ability checks that **failed** |
| `/dev/secpolgenerate/unused` | 3118 | the types and rules that were **not** exercised |
| `/dev/secpolgenerate/request` | 0 | the generator's request channel (empty) |
| `/dev/secpolgenerate/control` | 0 | the generator's control channel (empty) |

The delta is stated against policy id `9b76fb65` — the id of
`qnx/latch.secpol` as compiled by `secpolcompile` into `qnx/build/secpol.bin`.

The workload completed under the generated policy: **235 proposals
received**, rung `HP` → `ADVISE` → `LATCH`.

## 2. How to read the delta

**The delta is a SUPERSET, and it is an OBSERVATION — not a rule set.**

Two independent reasons, and both must be subtracted before the delta means
anything about the deployment policy:

1. **The audit image is UNRESTRICTED.** `-u` means the generator allows
   behaviour that the enforced policy forbids, so the generator's model of
   "what this system needs" is wider than what the deployment needs. It
   includes what the **development-only** binaries did: `secpolgenerate`
   itself, `secpol-preload.so`, `libsecpol-gen.so.1` and the audit reader
   `latch_secpol_dump` are all present in this image and absent from the
   deployment image.
2. **The workload is one scenario.** Only the 235-frame scripted guest
   scenario ran. Everything else is out of scope (see §6).

Every entry below is therefore classified, and **the default disposition is
"not accepted"**.

## 4. The errors file — one error, and it must NOT be "fixed"

The generator reported exactly **one** failed ability check:

```
1970-01-01 00:00:00 procnto-smp-instr (pid:1 type:default) failed to use ability latch/propose as root
```

with the proposed rule:

```
allow default self:ability {
    latch/propose
};
```

**This is the least-privilege boundary working, not a defect.** `default` is
the type of anything that has not been explicitly typed — here, the
untyped startup shell's `waitfor /dev/latch/proposal`. Attaching to the
supervisor's proposal node requires `latch/propose`, which `default` does
not hold. The visible symptom is the startup line
`Unable to access "/dev/latch/proposal" (1)` in the console transcript.

**Disposition: REJECT the generated rule.** Accepting it would grant the
*propose* ability to **every untyped process on the system** — precisely the
widening the custom-ability design exists to prevent. The correct fix is
none: the startup script's `waitfor` is a convenience probe, and the
resource manager creates the node a moment later regardless.

## 5. The one actionable finding — recorded, not applied

`qnx/latch.secpol` grants `qvm_host_t` the **unrestricted** `settypeid`
ability (line 128). The generator observed exactly one type transition made
by `qvm_host_t`:

```
settypeid:latch_ingest_t
```

and that matches the buildfiles exactly: all four profiles start the guest
ingest with

```
hostdev >"|on -T latch_ingest_t -C 1 -p 30f /proc/boot/latch-ingest …"
```

(`qnx/latch_qemu_virt.qvmconf`, `latch_qemu_governor.qvmconf`,
`latch_qemu_infer.qvmconf`, `latch.qvmconf`). There is no second target.

So the recommendation is:

> Narrow `qvm_host_t`'s `settypeid` to `settypeid:latch_ingest_t`.

**Why it is not applied in this pass.** The audit's whole finding is that
its observation is a **superset** and its coverage is **partial** (§2, §6).
Adopting a rule derived from a superset, on the strength of one run, is
exactly the mistake this audit exists to prevent. The narrowing must be
validated against the **enforced** image on target, where the ability
check actually happens:

```bash
make -C qnx ifs-qemu-governor GUEST_IMAGE=/abs/path/to/Image
make -C qnx verify-governor-qemu          # the 235-frame scenario
make -C qnx ifs-qemu-aarch64 GUEST_IMAGE=/abs/path/to/Image
python3 tools/verify_qemu_aarch64.py      # the 84-frame legacy scenario
```

Both scenarios must pass with the narrowed rule before it is adopted, and
the change belongs in its own reviewed commit — not inside an audit whose
own output is still being reconciled.

**One caveat that must travel with the recommendation:** `latch_guestd_t`
holds `settypeid:qvm_host_t` (`qnx/latch.secpol` line 149), and the
guest-lifecycle daemon spawns `qvm`. That is a *different* type's
`settypeid`, and it is already narrow. Narrowing `qvm_host_t` does not
touch it.

## 6. The unused file is NOT a removal list

The `unused` file lists types and rules the generator believes were not
exercised: `guest_ctl_t`, `i2c_t`, `latch_verify_t` and `latchctl_t` were
unused **types**, and it lists a long set of abilities per type — including
`latch/actuator` for `latchd_t` and `channel_connect:latchd_t` for
`latch_ingest_t`.

**Both of those contradict facts this very run establishes:**

- `latchd_t` **did** own the actuator node and **did** exercise the
  actuator path — 235 proposals were received and applied;
- `latch_ingest_t` **did** connect to `latchd_t` — that is how the 235
  frames arrived.

So the `unused` report is **not** a faithful list of what the workload did
not touch. It is the generator's model, produced while the system ran in
**unrestricted** mode (`-u`), in which ability checks are bypassed and
therefore cannot be observed as "uses" in the way the enforced image would
observe them.

**Disposition: nothing may be removed from `qnx/latch.secpol` on the
strength of this file.** The correct reading of the `unused` output is:

> **the audit's coverage is partial, and the file proves it.**

The rules that the workload genuinely did not exercise are the ones the
review must enumerate by hand — and that list is in §7.

## 7. What this audit does NOT prove

This is the part a judge must read, so it is stated explicitly:

- **The workload is one scenario.** The 235-frame scripted guest scenario
  on the GOVERNOR profile, in mock-I²C mode, under TCG. Nothing else ran.
- **Not covered: the I²C plant.** `i2c_t` and the `latchd_t → i2c_t`
  channel rule were never exercised — the QEMU target runs `latchd -n`
  (mock mode; no PCA9685 is present). The `i2c_t` block is **UNKNOWN**,
  not safe.
- **Not covered: the Raspberry Pi 4B board.** No Pi BSP is installed on
  this workstation; the Pi buildfile exists but cannot be built here. The
  Pi's `i2c-bcm2711` path is **UNKNOWN**.
- **Not covered: the guest-lifecycle channel.** `guest_ctl_t` was unused:
  the audit workload never ran `latchctl guest-restart`, so the
  `guest_ctl_t` attach rule and both of its channel-connect rules were
  never exercised by this run. They are covered by a *different* capture
  (`docs/evidence/governor/governor-vm-kill-resume.txt`), not by this one.
- **Not covered: the legacy 84-frame verifier and `latch_verify_t`.**
  `latch_verify` does not run in the GOVERNOR profile. Its rules are
  **UNKNOWN**.
- **Not covered: `latchctl_t`'s actuator ability.** `latchctl` was spawned
  by the operator shell during the audit (for `status`), and its type
  appears as unused. `latchctl`'s `latch/actuator` grant and its
  `hold`/`grant-check` behaviour are covered by the VM-kill capture, not
  by this run.
- **Not covered: any failure path.** The supervisor's LATCH rung was
  reached, but only through the scripted lease expiry — not through a
  malformed frame, a replayed frame, a foreign writer, an I²C error or a
  privilege probe.
- **Not covered: the `default` type's other uses.** Only one `default`
  ability check was observed.

**A rule this audit never touched is UNKNOWN to it, not SAFE.**

## 9. Post-Audit Enforced Validation (`M-10`)

§8 said the one actionable recommendation — narrow `qvm_host_t`'s
unrestricted `settypeid` to `settypeid:latch_ingest_t` — was to be
validated on the **enforced** image "in its own reviewed change". This
section is that change's validation record.

**What was changed.** `qnx/latch.secpol` — `qvm_host_t` now holds
`settypeid:latch_ingest_t` instead of the bare `settypeid`. Nothing else
in the policy changed. The proposal channel type was deliberately **not**
split: that is a separate policy change with its own on-target
requirements, so it is recorded here rather than applied.

**What was measured, and where.** The enforced QNX AArch64 `virt` image
(`qnx/latch_qemu_governor.build`, whose buildfile pushes the compiled
policy with `secpolpush`) was booted on 2026-11-28 from the tree that
carries the narrowing. The evidence is the archive's own transcript,
`docs/evidence/governor/governor-vm-kill-resume.txt`, refreshed by that
run:

| observation | result |
|---|---|
| the policy was **ENFORCED**, not merely compiled | `latchctl grant-check` from the operator shell printed **DENIED**, and the supervisor counted `EPERM Rejections: 1`. The least-privilege boundary was live during the run, so a permitted transition is a fact about an enforced policy and not about an unenforced one. |
| the boot-time transition | `qvm_host_t` → `latch_ingest_t` was permitted. The qvmconf's `hostdev >"\|on -T latch_ingest_t …"` spawn succeeded, the ingest opened the proposal node and the guest streamed (`[GUEST ACTIVE] Successfully received 53 proposals from Linux guest VM`). A refused transition would have produced no ingest and therefore no stream at all. |
| the transition after a **RESTART** | the lifecycle daemon's `latchctl guest-restart` re-launched qvm (`generation 2`), the new qvm spawned a new ingest under the same scoped rule, the restarted guest streamed again (`[VERIFIED] The new session is streaming (rx 106 -> 114)`) and the supervisor reported a **NEW** writer session (`Session Gen: 1 -> 2`, `Writer Held: 1`). |
| the **NEGATIVE** transition | **NOT demonstrated.** No shipped image attempts a transition into `latchd_t`, so the refusal is a property of the policy text, not an observed target event. |

The negative case is the important limit and it is stated rather than
papered over. "The bare `settypeid` is gone" is proved by the policy and
by the gate (`tools/consistency_check.py` requires the scoped form **and**
the absence of the bare form, and two mutations cover the two halves
separately). "A transition into `latchd_t` is refused" is proved
**off-target**, by that gate's own derivation. Demonstrating it on target
would need a disposable image whose qvmconf deliberately asks for a
transition the policy forbids — and a deliberately-malicious image is not
something this repository ships, so the claim is not made.

**A LATER capture of the same scenario did not complete, and it is
recorded rather than hidden.** The VM-kill + restart capture
(`make -C qnx evidence-governor-vm-kill`) was run a second time against
this same enforced image later the same day. PHASES 1-11 passed —
including the operator's `latchctl guest-restart`, the guest status read
through a read-only open, and the new writer session — but PHASE 12 (the
restarted guest must stream again) did not: the restarted guest Linux
delivered no frame within the harness's 120 s window (`rx 406 -> 406`).
The cause was the **workstation**, not the policy: the host had ~190 MiB
of free RAM and ~18 GiB of swap in use while that capture ran, and QEMU
had been asked for 2 GiB of guest RAM. A memory-exhausted host cannot
boot a Linux guest in any bounded time — the same class of failure as the
TCG measurement in AGENTS.md §4d. That run wrote **no** archive file (the
harness writes the archive only on success), so it claims **no** PASS,
and the transcript quoted above is the earlier, complete one.
